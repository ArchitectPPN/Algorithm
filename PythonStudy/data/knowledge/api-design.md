# API 接口设计原则

## RESTful 设计

- URL 使用名词复数，如 `/users`、`/orders`
- 用 HTTP 方法表达操作：GET 查询、POST 创建、PUT 更新、DELETE 删除
- 嵌套资源用路径表达，如 `/users/{id}/orders`
- 避免在 URL 中放动词，如 `/getUser` ❌ → `GET /users/{id}` ✅

## 状态码规范

- 200：成功（GET/PUT/PATCH）
- 201：创建成功（POST）
- 204：成功但无返回内容（DELETE）
- 400：客户端请求错误（参数校验失败）
- 401：未认证（需要登录）
- 403：无权限（已登录但无权访问）
- 404：资源不存在
- 422：请求格式正确但语义错误（业务校验失败）
- 500：服务器内部错误

## 版本管理

- URL 路径版本：`/api/v1/users`（推荐，简单直观）
- 请求头版本：`Accept: application/vnd.api.v1+json`（适合大型 API）
- 版本升级时保持向后兼容，至少保留一个旧版本
- 废弃的 API 要在响应头中标记 `Sunset` 和 `Deprecation`

## 请求与响应

- 请求参数：路径参数用于标识资源，查询参数用于过滤/排序/分页
- 分页参数：`page` + `page_size`，或 `offset` + `limit`
- 响应格式统一：`{code, message, data}` 或 `{status, data, error}`
- 错误响应要包含：错误码、错误信息、可能的修复建议

## 安全规范

- 所有接口必须使用 HTTPS
- 敏感操作需要二次认证（如修改密码、删除数据）
- 请求限流：防止暴力攻击，如每分钟 60 次
- 输入校验：所有客户端输入都要校验，不信任任何外部数据
- 日志脱敏：密码、token 等敏感信息不能出现在日志中
