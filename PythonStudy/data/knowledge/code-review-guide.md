# 代码评审规范

## 评审流程

- 每次改动都要发合并请求（MR/PR），禁止直接推送到主干
- PR 描述写清楚：改了什么、为什么改、怎么测试
- 小步提交：一个 PR 只做一件事，控制在 300 行以内
- 评审通过 + CI 绿勾才能合并

## 评审关注点

- 逻辑正确性：边界条件、空值、异常分支有没有处理
- 可读性：命名是否清晰、函数是否单一职责、注释是否解释"为什么"
- 安全性：有没有注入、越权、敏感信息泄露风险
- 性能：有没有 N+1 查询、循环里建对象、不必要的大对象拷贝

## 评审方式

- 评论要具体：指出问题和改进方向，不要只说"看不懂"
- 给建设性建议，不攻击人：评审代码，不评审作者
- 用提问引导思考：`这个边界情况考虑了吗？` 而不是 `你写错了`
- 阻塞性评论（必须改）和可选建议要分开标注

## 反面案例

- ❌ `for` 循环里频繁操作数据库 → 批量查询替代
- ❌ 全局状态被多处修改 → 明确数据流，限制可变性
- ❌ 吞异常后静默返回默认值 → 至少打日志
- ❌ 硬编码的魔法数字 → 命名常量

## 评审后的处理

- 作者收到评论要逐个回应：已修复 / 解释原因 / 有分歧的讨论
- 修复后再请求评审，循环直到无阻塞问题
- 合并前确认：测试通过、文档同步、无遗留 TODO
- 评审中学到的规范沉淀到团队文档，形成知识资产
