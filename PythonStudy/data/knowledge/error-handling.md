# 错误处理最佳实践

## 异常捕获原则

- 捕获具体异常，不要裸 `except:` 或 `except Exception:`
- 只捕获你能处理的异常，处理不了就让它往上抛
- 不要用异常做流程控制（如用 try/except 代替 if/else 判断字典 key）
- 异常信息要包含上下文：`raise ValueError(f"用户 {user_id} 不存在")` 而非 `raise ValueError("用户不存在")`

## 日志规范

- 使用 `logging` 模块，不要用 `print`
- 日志级别：DEBUG（调试信息）、INFO（关键流程）、WARNING（可恢复的异常）、ERROR（需要关注的错误）、CRITICAL（系统级故障）
- 异常日志要包含完整堆栈：`logger.error(f"处理订单失败: {order_id}", exc_info=True)`
- 日志格式统一：`[时间] [级别] [模块] 消息`
- 敏感信息脱敏：密码、token、身份证号不能出现在日志中

## 降级策略

- 非核心功能失败时，降级而非报错（如推荐服务挂了，返回热门列表）
- 超时控制：所有外部调用必须设超时，避免无限等待
- 重试机制：网络抖动可重试，但必须有上限（2-3 次）和退避策略（指数退避）
- 熔断器：连续失败超过阈值时短路，直接走降级，避免雪崩
- 重试不是目的，降级才是工程解——重试是争取成功，降级是保证系统不崩

## 错误传播

- 底层错误要包装后再抛：`raise ServiceUnavailableError("用户服务不可用") from e`
- 不要吞异常：`except: pass` 是最危险的代码
- API 层统一错误响应格式：`{code: 500, message: "内部错误", request_id: "xxx"}`
- 给用户友好的错误提示，不要暴露内部实现细节

## 防御性编程

- 所有外部输入都要校验（API 参数、配置文件、数据库查询结果）
- 使用类型注解 + Pydantic 做运行时校验
- 关键操作前检查前置条件（如删除前检查记录是否存在）
- 幂等设计：同一请求执行多次结果相同，防止重复提交
