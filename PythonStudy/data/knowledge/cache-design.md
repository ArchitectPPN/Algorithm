# 缓存设计

## 缓存策略

- 读多写少的场景才适合加缓存，写多的加缓存反而增加一致性负担
- 热点数据用本地缓存（进程内），分布式数据用 Redis
- 缓存 key 要包含版本号或业务前缀，避免不同业务冲突
- TTL 不能太长：黄金 5 分钟，超长缓存要主动刷新

## 缓存穿透

- 问题：查询不存在的数据，每次都打到数据库
- 解决：缓存空值（短 TTL）；布隆过滤器拦截明显不存在的 key
- 参数校验在前，非法参数直接拒绝不进缓存

## 缓存击穿

- 问题：某个热点 key 过期瞬间，大量请求同时打到数据库
- 解决：加互斥锁，只有一个请求回源，其余等待；或后台线程主动预热
- 用「逻辑过期」代替「物理过期」，后台统一刷新

## 缓存雪崩

- 问题：大量 key 同时过期，数据库被瞬间压垮
- 解决：过期时间加随机偏移（TTL = 基准 + random）；多级缓存
- 本地缓存 + Redis 两级，Redis 挂了本地还能兜底

## 一致性

- 写操作先更新数据库，再删除缓存（Cache Aside 模式）
- 删除缓存失败要重试，或订阅 binlog 异步清理
- 不追求强一致：缓存可以短暂脏，但要定义可接受窗口
- 缓存和数据库的一致性，永远是缓存设计最难的部分
