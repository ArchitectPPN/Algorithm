## 参考解答（自测完再对照）

### 一句话讲清楚 · 参考解答

**Q1. Embedding 是什么？**

Embedding 是把文本转成一个数字向量（比如 768 维），目的是让"语义相近的文本在向量空间里也相近"。

关键点：它不是随机编码，而是**从海量语料里学出来的语义映射**。训练时，模型见过"苹果"和"香蕉"经常出现在相似的上下文里（水果、超市、吃），所以它们的向量被"挤"在一起；而"苹果"和"数据库"上下文差异大，向量就离得远。

类比：词向量相当于给每个词安排一个"语义经纬度"。北京和上海都在中国→坐标近；北京和纽约→坐标远。Embedding 学到的就是这种"语义地图"。

**Q2. 为什么需要分片？**

三个原因：
1. **上下文窗口限制**：embedding 模型和 LLM 都有 token 上限，整本书塞不进去
2. **语义稀释**：一段 5000 字的文本压成一个向量，"主题"被平均掉了，检索时哪部分都抓不准
3. **检索粒度**：用户问的往往是"一个问题"，需要返回"一段针对性内容"，而不是一整篇文章

**Q3. overlap 为什么不能根治句子截断？**

overlap 只是让"卡在边界的关键句"有机会同时出现在相邻两段里，是一种**补丁**。它无法保证所有句子都完整——任何固定长度切分都会有句子被切断，overlap 只能降低概率，不能消除。根治方案是按标题/段落等**语义边界**切分。

**Q4. Chroma 和传统数据库的区别？**

| 维度 | MySQL | Chroma |
| --- | --- | --- |
| 存什么 | 文本、数字（结构化） | 向量（float 数组）+ 可选元数据 |
| 怎么查 | `WHERE name='张三'` 精确匹配 | 给一个向量，找最相似的 N 个 |
| 查什么 | 精确值/范围 | 语义相似度 |
| 索引 | B-Tree | ANN（HNSW 近似最近邻） |

本质区别：**MySQL 回答"哪个值等于 X"，Chroma 回答"谁最像 X"**。一个是等号语义，一个是相似度语义。

**Q5. L2 和余弦相似度的区别？RAG 推荐哪个？**

- **L2（欧几里得距离）**：两点直线距离，**受向量长度影响**，范围 [0, +∞)
- **余弦相似度**：只看方向夹角，**对文本长度不敏感**，范围 [-1, 1]

RAG 推荐余弦，两个原因：
1. 知识库片段长度不统一（100 字 vs 500 字），L2 会被"长度"干扰，余弦只看语义方向
2. 余弦有固定范围，阈值好定（0.5 起步），L2 无上界，每个项目都要重新校准

> 补充：如果 embedding 已归一化（nomic-embed-text 就是），L2 和余弦的**排序结果完全等价**，差异只在阈值可操作性上。

**Q6. 距离阈值怎么定？**

L2 距离没有固定上界，不是拍脑袋定的，三种系统化方法：

| 方法 | 原理 | 是否需要标注 |
| --- | --- | --- |
| **余弦相似度** | 有固定范围，0.5 当通用起步值 | 否 |
| **Elbow Method** | 距离排序，找"突然跳变"的拐点 | 否 |
| **已知答案校准** | 用提前知道命中的查询，找相关/不相关分界 | 是 |

我们跑出的 350 是"已知答案校准"的结果：相关结果距离 209~232，不相关 300~390，分界点在 330~360 → 取 350。

**Q7. RAG 的完整流程？**

加载 → 分片 → 向量化 → 存 Chroma → 用户查询 → 查询向量化 → 相似检索 → 阈值过滤 → 返回 Top-K 片段。

一句话："**文档加载→分片→向量化→存向量库；查询时把问题也向量化，找最像的 N 段返回。**"

### 回答追问 · 参考解答

**Q8. 为什么不用关键词匹配而用 Embedding？**

关键词匹配是**字面**匹配：查"登录"匹配不到"认证"、"鉴权"、"session"。Embedding 是**语义**匹配：能理解"登录失败"和"认证异常"说的是同一件事。

关键词适合精确词、规范术语；Embedding 适合自然语言、口语化提问、同义词场景。真实 RAG 系统常用**混合检索**（关键词 + 向量）互补。

**Q9. chunk_overlap 设多大合适？**

经验值是 **chunk_size 的 10%~20%**（如 500 字配 50~100 字重叠）。但要点是理解它的本质——overlap 是"防关键信息卡边界"的补丁，不是"提高语义完整度"的正解。片段越大 overlap 可以越小（因为句内信息冗余高了）。

**Q10. 检索结果不相关，可能的原因？**

从内到外排查：
1. **知识库没收录**：文档里根本没有相关内容 → 检索再准也找不到（最常被忽略）
2. **分片不合理**：chunk 太大语义被稀释，或句子被切断导致关键信息丢失
3. **embedding 模型不匹配**：中文文本用英文优化的模型，语义理解差 → 换 bge 这类中文模型
4. **阈值太松**：`top_k` 强制返回 N 条，不相关的也凑数进来 → 加距离阈值过滤
5. **查询表达差异大**：用户问法太口语化/抽象，和文档用词完全不同 → 查询改写（同义词扩展 / HyDE）
6. **元数据干扰**：检索被无关的 metadata 过滤条件影响

排查顺序：**先确认知识库有没有这内容 → 再看片段切得对不对 → 再试阈值和模型 → 最后考虑改写查询**。

**Q11. Embedding 模型能本地跑吗？生产环境怎么选？**

能。本地用 Ollama 跑开源模型（nomic-embed-text、bge-small-zh、bge-m3），零成本零延迟，数据不出内网。

生产环境选择维度：

| 场景 | 选择 |
| --- | --- |
| 数据敏感、要求离线 | 本地开源模型（bge 系列） |
| 追求极致效果、预算充足 | 云 API（智谱 embedding-3、通义） |
| 中文为主 | bge 中文系列 / 中文优化的云 API |
| 兼顾成本与效果 | 本地开源起步，用评估指标验证，不够再上云 |

核心原则：**用数据说话**——建一批"已知答案"的测试查询，实测各模型的 Recall@K，而不是看宣传参数。
