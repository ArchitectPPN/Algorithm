### 自测参考答案（2026-08-15 复盘）

> 这两题是"回答追问"里最容易答错、最能区分"背了还是懂了"的，把讨论结论落下来便于回顾。

**Q：能混用两个 embedding 模型的向量吗？为什么？**

不能。**同一 Chroma 集合里的所有向量，必须来自同一个 embedding 模型**。两层原因：

1. **维度对不上 → 直接没法算**：A 模型 512 维、B 模型 768 维，拿 768 维向量给 A 模型集合根本存不进、余弦也算不了。
2. **⚠️ 维度对得上也不能混用**（这才是真坑）：即使两个模型恰好都是 1024 维，**每一维代表什么含义是模型自己训练出来的**。bge-m3 的第 50 维可能编码"是否和数据库相关"，另一个模型的第 50 维可能编码"是否和 API 相关"——同样 1024 维，但两套坐标系完全不是一回事。拿 bge-m3 的查询向量去和另一个模型的文档向量算余弦，等于"用英语坐标查法语词典"，数字上能算出相似度但毫无意义。

> 一句话：**向量空间是模型私有的**。维度只是向量长度，语义空间才是关键。这也是 Day38 建了 `kb_nomic` / `kb_bge` / `kb_zhipu_2048` 三个独立集合的原因——每个模型一个独立空间，互不污染。

**Q：Recall@5=100% 但 MRR=0.3，说明什么？该往哪个方向优化？**

先把两个指标的"问什么"钉死：

| 指标 | 问的是 | 命中条件 |
|------|--------|---------|
| Recall@K | "找没找到？" | 正确答案出现在前 K 条就 ✅（不管排第几） |
| MRR | "排得靠不靠前？" | 排第 1 得 1.0，排第 2 得 0.5，排第 5 得 0.2…越靠后分越低 |

连起来读：**每次都能找到正确答案（Recall 满分），但它总被埋在第 3、4 名（MRR=0.3 大概对应平均排第 3~4 位）——有，但不好用**。类比：图书馆要的书每次都在架子上，但每次都藏在第 4 排要翻半天。

**优化方向：改排序，不要动召回。**

- MRR 低 = 排序质量差，正确答案在但没排到前面 → 该调排序
- ✅ 改输入（Day39 HyDE/同义词改写，让查询向量更接近正确文档 → 排名往前）
- ✅ 改检索（Day37 MMR 重排；Day36 `where` 过滤掉干扰项）
- ✅ 加精筛（Day34 LLM rerank：粗筛靠余弦、精筛靠 LLM，专门治"排位靠后"）
- ❌ **不该换 embedding 模型**（Day38）：Recall 已 100% 说明召回没问题，换模型是高成本动作却不解决排序问题——**Recall 满分时换模型是错误优化方向**

> 两个指标的分工：Recall 管"有没有"，MRR 管"好不好用"。Recall 满分 + MRR 低 → 召回没问题、排序有问题 → 调排序（改输入/精筛），不要动召回。

#### 深挖：Recall@K=100% 到底说明什么？

字面意思：**测试集里每一条查询，正确答案都混在前 K 条结果里了，一条都没漏**。但它只回答**一个问题**，别让它替你回答更多：

| 它说明了 | 它不说明 |
|---------|---------|
| ✅ 召回没问题——正确答案都被找回来了，没被漏掉 | ❌ 正确答案排第几（那是 MRR 的事） |
| ✅ embedding 模型 + 检索链路能把目标文档"拉进候选池" | ❌ 排序好不好（Recall 100% 也可能排第 5） |
| ✅ 阈值没设太严（没把正确答案误杀掉） | ❌ 候选池里有没有噪音（只管"正确答案在不在"，不管"旁边站着谁"） |

图书馆类比：Recall@5=100% = 你要的书每次都在前 5 排架子上。但它藏在第 4 排还是第 1 排？前 5 排里另外 4 本是不是噪音？Recall 都不告诉你。

**两个常见误读**：
1. "Recall 100% = 检索系统很好" → 错。只说明"能找到"，不代表"好用"。Recall 100% + MRR 0.3 就是典型"能找到但不好用"。
2. "Recall 100% 就该满意了" → 看下游怎么用结果：
   - 下游是**人看 Top-5**（搜索结果页摆 5 条）→ Recall@5=100% 够用，MRR 低也能接受
   - 下游是**喂给 LLM 当上下文**（RAG 场景，Day40 `/ask`）→ MRR 低就有麻烦：正确答案排第 5，前面 4 条噪音混进 prompt，LLM 容易被噪音带偏、或 context 太长把正确信息稀释。**RAG 里 MRR 和 Recall 一样重要**

> 一句话收口：**Recall@K=100% 说明"召回合格、别再动召回"，剩下的问题交给 MRR 去暴露、交给排序优化去解决。**

#### 为什么要召回？（Recall 这个指标的底层意义）

检索系统分两步：**①召回（从全库里捞一个候选小池子）→ ②排序（在小池子里排先后）**。Recall 测的是第①步。

为什么这一步值得单独拎出来评估？三个原因：

1. **召回是"上限定者"**：如果正确答案在第①步就被漏掉了，后面排序再厉害也救不回来——**你不可能把一个没被召回的东西排到前面**。所以 Recall 是检索系统的天花板：Recall 不行，MRR 再高也是虚的（MRR 高只是说明"被召回的那部分排得好"，但漏掉的部分它根本没看见）。
2. **两步用的方法不同、成本不同**：召回要扫全库（几千几万条），必须快，所以用向量近似检索（粗，可能漏）；排序只在候选小池子里跑（几十条），可以用更准但更慢的方法（MMR、LLM 精筛）。**Recall 专门盯"粗筛有没有漏掉真东西"**——这是向量检索最容易出问题的地方，所以值得单独评估。
3. **召回错和排序错的修法完全不同**：Recall 低 = 漏了 → 改召回（换 embedding 模型 / 改查询 / 松阈值 / 扩候选池）；MRR 低 = 排错了 → 改排序（HyDE / MMR / 精筛）。**不分开评估就会乱投医**——Recall 低时去调排序，等于在没召回的东西上排先后，纯属白费。

> 一句话：**召回管"上限"（漏没漏），排序管"体验"（排第几）。先保证 Recall 合格（不漏），再谈 MRR（排好）。** 这就是为什么评估要 Recall + MRR 一起看——各盯一个环节，缺哪个指标就会在哪个环节瞎优化。
