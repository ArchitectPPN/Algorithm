# Day 34 实战踩坑记录 — RAG Pipeline 三层过滤

> 今天把 `rag_pipeline.py` 从"纯余弦检索"升级成「余弦粗筛 → LLM 精筛 → 基于片段生成」的完整 RAG 流程，
> 过程中踩了 6 个坑。每一条都是真实踩过、有输出为证的。全部记下来，避免重踩。

---

## 坑 1：余弦 0.5 通用阈值挡不住无关查询

**现象**：知识库里没有"怎么做红烧肉"，但余弦检索照样返回 3 条垃圾（相似度 0.63-0.68）。

**根因**：nomic-embed-text 是英文模型、中文效果中等。中文里"完全不相关"的句子相似度也能到 0.6+。用已知答案校准，相关查询 top1 是 0.635-0.764，无关查询 top1 是 0.567-0.679——**两组大面积重叠，没有一个阈值能分开**。

**结论**：0.5 只是"通用起步值"，具体项目必须校准。更根本的是——**纯相似度阈值有数学天花板，必须靠 LLM 精筛**（这就是三层过滤的意义）。

---

## 坑 2：切余弦度量后必须重建索引

**现象**：在 `get_or_create_collection()` 里加了 `metadata={"hnsw:space": "cosine"}`，但查询结果还是 L2 的。

**根因**：Chroma 的 `get_or_create_collection` 对**已存在的集合不会应用新 metadata**。只有新建集合才生效。

**解决**：`build_index(rebuild=True)`（先 `delete_collection` 再重建），并确认 `collection.metadata` 显示 `{'hnsw:space': 'cosine'}`。

---

## 坑 3：推理模型 num_predict 给太少 → 返回空字符串

**现象**：用 deepseek-r1 做精筛，`num_predict=10` 时返回 `''`（空），怎么调都不出结果。

**根因**：deepseek-r1 是**推理模型**，回答前会先生成一大段思考（reasoning）。`num_predict` 是输出 token 上限，思考就把配额占满了，**正文还没输出就被截断**，导致 response 为空。

**解决**：`num_predict=400` 给足，R1 思考完能正常输出，且**判断最稳**。

**排查技巧**：遇到 LLM 返回空，先分步测——单独调用 vs 循环调用、简单 prompt vs 复杂 prompt，逐层定位是解析问题、超时问题还是 token 配额问题。

---

## 坑 4：小模型 lfm2 不遵守二分类指令

**现象**：让 lfm2 "只回答：相关 或 不相关"，它输出 `'相关'`、复述片段（`'"SELECT * FROM users'`）、写解释（`'和其后的分支策略...'`）各种跑偏，5 条垃圾全被误判成"相关"。

**根因**：lfm2 参数太小，对"只输出两个字"这类强约束指令执行不稳定。

**结论**：**精筛模型的选择很关键**。小模型省钱但判断不可靠；强约束指令 + 严格解析（默认不相关）是兜底。

---

## 坑 5：`"不相关".endswith("相关")` 是 True —— 中文子串陷阱

**现象**：改了解析逻辑用 `cleaned.endswith("相关")` 判断，结果所有"不相关"都被误判成"相关"，精筛通过率暴增。

**根因**：`"不相关".endswith("相关")` → **True**！因为"不相关"确实以"相关"结尾。这是中文里极隐蔽的子串 bug。

**正确写法**（必须先排除"不相关"再判断）：
```python
if "不相关" in tail:
    is_relevant = False
elif "相关" in tail:
    is_relevant = True
else:
    is_relevant = False
```
⚠️ 另一个隐藏坑：R1 有时输出 `'无关'`（不含"相关"），上面逻辑会走 else → 不相关，行为正确但最好显式兼容。

**教训**：任何"判断文本是否含某词"的逻辑，先想清楚**否定的词会不会包含肯定的词**（相关/不相关、可用/不可用……）。

---

## 坑 6：精筛放行垃圾片段 → 生成环节编造答案

**现象**：精筛被 lfm2 全放行后，问"怎么做红烧肉"，deepseek-r1 竟基于不相关的错误处理片段，**编造出**"五花肉、酱油、老抽、八角桂皮……"的菜谱。

**根因**：RAG 里**上下文片段不相关时，LLM 会强行圆场**——它不会说"我没资料"，而是顺着编。这是 RAG 最危险的失败模式（幻觉源头）。

**解决**：① 精筛用可靠的 R1，确保放进上下文的都是真相关片段；② 生成 prompt 明确"只能根据片段回答，片段不足就说没有"。

**这是今天最重要的一课**：**RAG 的准确性不取决于生成模型有多聪明，取决于检索到的片段有多可靠。检索是上限。**

---

## 最终方案（三层过滤）

```
用户查询
  │
  ├─ 第1层 余弦粗筛：search()  min_similarity=0.5（宁松勿紧，多取候选）
  │     ↓ 5 条候选
  ├─ 第2层 LLM 精筛：rerank()  deepseek-r1:7b，num_predict=400，从尾部提取结论
  │     ↓ 只放行"相关"
  └─ 第3层 生成：generate()   deepseek-r1:7b，基于相关片段回答，不足则拒绝编造
```

**验证结果**：
- 知识库内查询"如何防止 SQL 注入" → 精准命中 sql-best-practices，回答准确 ✅
- 知识库外查询"怎么做红烧肉" → 精筛全拦截，回答"知识库中没有相关内容" ✅ 不编造
