# Pi 学习计划 v2（RAG 暂停期主线）

> **一句话目标**：读懂 Pi 的 agent 内核（约 2,100 行），并把它四个可迁移设计落到自己的 `agent/` 项目里，产出可演示的改造与可量化数据。
>
> **配套读物**：`docs/notes/pi-architecture-analysis.md`（架构与定位）、`docs/notes/pi-code-reading-guide.md`（逐文件行号级导读）、`docs/notes/agent-harness-gap-analysis.md`（九项能力缺口）。
>
> **版本说明**：v1 按 6 天 × 2h 设计，实测后判定工期不足——七站精读约 3,100 行加两项结构改造，真实投入约 20–24h。v2 改为三档方案，按可投入天数选择。

## 零、完成定义：不是"读完"，是能答出这八问

学 Pi 的常见失败是"看完就忘"，因为把"读过"当成了"学会"。本计划用三条硬标准验收，全部满足才算完成：

| 层次 | 标准 | 检验方式 |
|---|---|---|
| **能读** | 能不看代码说清 `runLoop` 的骨架与两个退出条件 | 白纸默写 |
| **能改** | 改造后的 `agent/` 跑通，且有一项前后对比数据 | `git log` + 数字 |
| **能讲** | 三个取舍能撑住追问（各 3 分钟） | 面试卡 + 自测题 |

`pi-code-reading-guide.md` 第十节的八道自测题是**唯一验收题库**。能连续答对六题以上，才算真读完；答不上来的题，就是没读懂的位置。

## 一、三档方案，按你的可投入天数选

| 档 | 内容 | 工期 | 拿到的产出 | 适合 |
|---|---|---|---|---|
| **最小** | 站 1–3（types、agent-loop）→ 渐进披露改造 | 6 天 / 12h | loop 对照表 + **1 个 token 降幅数字** | 只能挤出 6 天空档 |
| **标准（推荐）** | 站 1–4 + 消息三态 + 事件归约 + 渐进披露 | 12 天 / 24h | 三项结构改造 + 2 个数字 + 8 题能答 | 想真正吃下内核 |
| **完整** | 标准 + 会话树 PoC + 压缩修正 + codemode | 18 天 / 36h | 一个可演示的作品级改造 | 目标是把 Pi 当简历主项目 |

**推荐标准档**，理由有三条：

1. **最小档缺"结构证据"**。只改 skill 加载，改造幅度是"一个函数"，面试撑不起"我理解 agent 架构"这句话。
2. **完整档的边际收益递减**。会话树、codemode 的价值高，但它们依赖消息三态与事件归约先落地——先做结构，后面才不是返工。这三项可以放到标准档之后单独排，不必一次吞下。
3. **12 天 ≈ 2.5 周**，与 RAG 软暂停腾出的窗口大致匹配，不需要改动 `transition-plan` 的周次结构。

### 为什么"消息三态"排在"会话树"前面

会话树需要每条 entry 有 `id` / `parentId`，而当前 `message.py`（75 行）连 `terminate` / `isError` / `durationMs` 三态都没有。**在错误的消息模型上建树，等于给流沙打地基。** 顺序不能颠倒。

## 二、标准档日程（12 天 × 2h）

每天的结构固定：读（40–60 min）→ 记（20 min）→ 落（40 min 代码或图）。"读"必须带产出，"记"必须写进 `docs/notes/`，"落"必须能跑。

### 阶段一：读通内核（Day 1–6，12h）

| Day | 读什么 | 时长 | 当日产出 | 完成判定 |
|---|---|---|---|---|
| 1 | `agent/src/types.ts` L1–260 | 2h | 「内部 AgentMessage / LLM 消息」两层投影图 | 说出 `convertToLlm` 为何是唯一转换边界 |
| 2 | `types.ts` L260–540 | 2h | 九回调表（时机 / 用途 / 不给会怎样） | 答出自测 2、6 |
| 3 | `agent-loop.ts` L111–390 | 2h | 默写 `runLoop` 双层骨架 | 不看代码写出两个退出条件 |
| 4 | `agent-loop.ts` L390–620 | 2h | 笔记：截断作废、并行三段式 | 答出自测 3、5 |
| 5 | `agent-loop.ts` L620–960 | 2h | 笔记：终止悲观聚合、工具集增量、abort 四点 | 答出自测 1、2、4 |
| 6 | `agent.ts` 全 623 行 | 2h | 「loop 发事件 → reducer 改状态」边界说明 | 答出自测 6 |

阶段一结束的标志：**八道自测题全部能答**。答不出的题回到对应文件重读，不要往下走——阶段二的改造全靠这层理解。

三个必须抓住的判断（每个都能直接当面试答案）：

- **没有 `max_rounds`**。收敛靠"模型不再调工具"或"整批 terminate"，不是计数器。你的 `max_rounds=30` 是安全网，Pi 认为那是提示词与工具设计的问题。
- **终止是悲观聚合**（`agent-loop.ts:700`）。一批三个工具，两个说停一个说继续 → 继续。任何一个认为还有事要做都被尊重。
- **截断时整批作废**（`agent-loop.ts:488`）。被 output limit 截断的参数可能"能解析但语义不完整"，执行比失败更危险。宁可全失败让模型重发。

### 阶段二：结构改造（Day 7–9，6h）

| Day | 改什么 | 时长 | 交付 |
|---|---|---|---|
| 7 | `message.py` 75 行 → 增 `terminate` / `isError` / `durationMs`，同步改 `agent_loop.py` 的构造点 | 2h | 现有 agent 全部工具跑通，无回归 |
| 8 | 事件归约层：把 `session_manager.py` 的"直接改状态"拆成 `事件 → reducer → state` | 2h | 事件类型枚举 + reducer 骨架 |
| 9 | 接上 reducer，`agent_end` 语义对齐（等所有监听器结算） | 2h | 端到端跑通，一条事件流可重放 |

这一步的风险最高，因为它动的是主链路。**建议单独开分支**（`git checkout -b refactor/pi-aligned`），失败可整体丢弃，不影响主线。

### 阶段三：可量化改造（Day 10–12，6h）

| Day | 做什么 | 时长 | 交付 |
|---|---|---|---|
| 10 | `skills.ts` L150–460 精读（发现规则 / 冲突处理 / `disable-model-invocation`） | 2h | 与 `loader.py` 的差异清单 |
| 11 | 改造 `loader.py`：整篇注入 → 只注入 name/description/location | 2h | 代码改动 + 回归测试 |
| 12 | 测 token 前后对比，写 3 张面试卡，更新 `pi-vs-myagent.md` | 2h | **一个可写进简历的数字** |

**Day 12 是整份计划唯一产生简历素材的一天**，不要跳过。测量方法：同一任务、同一模型，统计 system 部分的输入 token（本地 ollama 可用 `/api/chat` 的 `prompt_eval_count`），改造前后各跑 3 次取中位数。

## 四、与其它任务的排序

RAG 软暂停后有三个候选任务在争同一段时间，我的排序建议：

```
Pi 阶段一（Day1-6） → Pi 阶段二（Day7-9） → MCP client（1-2天）
   → Pi 阶段三（Day10-12） → 可观测性（2-3天） → 压缩修正
```

三条理由：

1. **结构改造必须先做**。Pi 阶段二会动 `message.py` 与 `session_manager.py`，而 MCP client 也要往工具注册里插东西。先改结构，MCP 接入一次成型；反过来则要改两遍。
2. **MCP client 卡在阶段二之后、阶段三之前**，是因为它是纯新增（1–2 天）不影响 Pi 的理解链，插在这里不会打断节奏。
3. **可观测性放在 Pi 之后**。它要统计 token 与工具成功率，而这些指标的口径正好是 Pi 阶段三测 token 时才建立起来的——先有测量习惯，再做埋点系统。

**RAG Day47–48 收尾**（1–1.5 天）建议留到最后单独补，或直接并入"完整档"之后。它不影响 Pi 这条线，但拖着会让 Week7 一直处于未收口状态。

## 五、边界：明确不学

| 不学 | 理由 |
|---|---|
| 写 TS 应用或 Pi 扩展 | 目标是搬设计，不是换栈 |
| 通读 42 篇官方文档 | 只需 `how-pi-works`、`session-format`、`skills`、`compaction`、`extensions` 五篇 |
| `coding-agent` 三个大文件（35KB / 37KB / 23KB） | 装包与 CLI 装配，与 agent 机制无关 |
| `tui` / `env` / `chord` / `telemetry` / `evals` 实现 | 表现层与运维层 |
| Durable 状态机实现 | 规模不匹配，只读设计文档 |
| 自研 TUI | Python 有 rich / prompt_toolkit |

**TS 语言门槛只需 2–3h**：类型注解、`async/await`，以及唯一必须专门补的**判别联合类型**（Pi 的条目全靠 `type` 字段分流）。不需要学装饰器、编译配置、前端框架。

## 六、风险与回退

| 风险 | 触发信号 | 应对 |
|---|---|---|
| 卡在 `agent-loop.ts` | Day 3 结束仍写不出骨架 | 不追求逐行，先默写骨架再看细节；必要时只读 L172–330 |
| 时间被工作挤占 | 连续 3 天没推进 | 降到最小档，保站 1–3 + 渐进披露，先拿到数字 |
| 改造引入回归 | 阶段二工具调用异常 | 分支隔离，整体回退；结构改造可延后，不硬推 |
| 读完就忘 | Day 6 后自测题答不出 4 题 | 回到八问清单定位薄弱点，不进入阶段二 |

**一个止损判断**：如果在 Day 9 结束时事件归约仍然跑不通，说明这次改造的规模超出了当前代码基础，**应停止并回退**，只保留阶段一的阅读笔记与阶段三的 token 数据。半成品的事件层比没有事件层更糟。
