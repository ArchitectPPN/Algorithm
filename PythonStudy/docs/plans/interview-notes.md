## 转行认知校准（开始学习前必读）

### 1. PHP 没落 ≠ 你的能力没落
PHP 语言在下沉是事实，但作为后端开发真正值钱的是**可迁移能力**：
- 接口设计、数据库建模、缓存策略、并发处理
- 业务理解、系统拆分、状态流转设计
- 工程化：版本控制、部署、排错、监控

这些在 AI Agent 开发里**全部用得上**。Agent 开发的本质是"后端工程 + LLM 调用"，不是纯算法研究。带工程经验转行是优势，不是从零开始。

### 2. "AI Agent 大模型开发"岗位分三类，路径差很多

| 方向 | 做什么 | 需要能力 | 对我的难度 |
|------|--------|---------|-----------|
| **应用层 Agent 开发** ✅ 已选 | 用 API + 框架做业务 Agent（客服、数据分析助手、RAG 产品等） | 后端工程 + Prompt + RAG + 框架（LangChain/LlamaIndex/自研） | ⭐ 最适合，2-3 个月可上手 |
| **模型层 / 算法** | 训练、微调、对齐 | 数学、PyTorch、深度学习、论文复现 | ⭐⭐⭐⭐ 非科班短期很难 |
| **Infra / 平台** | 训练框架、推理优化、向量库、agent 编排平台 | C++/CUDA、分布式、底层 | ⭐⭐⭐⭐ |

**结论**：走应用层，充分发挥后端工程优势。

### 3. 常见误区
- 不需要先把 transformer 数学原理啃透才能面试应用层岗位 → 原理懂到"能讲清楚"即可，重点是工程能力。
- "用过 AI Agent 工具" ≠ "会开发 AI Agent" → 体感强是优势，但缺"从调度方写 ReAct loop / 自己搭 RAG 全链路 / 原理能讲清"这三块，需 2-3 个月补齐。

### 4. 建议学习路径
1. Python 速通（异步、类型注解、venv）
2. LLM API + Prompt 工程（调 OpenAI/Claude API，function calling，结构化输出）
3. RAG 全链路（切分、embedding、向量库、检索、重排、生成）
4. Agent 框架与模式（ReAct、工具调用、记忆、多步规划；LangChain/LlamaIndex 或自研）
5. 一个完整项目（端到端能跑的 Agent 应用放 GitHub——面试硬通货）
6. 原理补课（transformer 大概、注意力、token、上下文窗口、幻觉原因、SFT/RLHF/DPO 概念层）

## 模块 A：Agent 核心原理

### 题目 A1：Agent 内部怎么工作的？（以"读 list.py 改 bug"为例）

**我的回答**：Claude Code 没用其它模型做意图识别，直接把问题给大模型，大模型根据上下文让 Claude 执行读取文件命令，读取后结合修 bug 意图检查代码，确认后给修复方案。

**点评**：
- ✅ 抓住核心循环："模型决策 → 执行工具 → 结果回灌上下文 → 模型再决策"。这就是 ReAct 骨架，很多只会背书的人反而讲不出来。
- ✅ "不做独立意图识别，让模型在 system prompt + 工具约束下自己决定"——对，这叫"模型即决策器"，加分。
- ⚠️ **认知偏差**："让 Claude 执行读取文件命令"——混淆了两个执行者：
  - **大模型（Claude）**：决策"要读文件"、生成工具调用参数，但**不执行**，只输出指令。
  - **Agent 运行时（Claude Code 这个程序）**：真正去读硬盘、跑命令、拿文件内容。
  - 准确说法：大模型输出"调用 read_file 工具，参数 list.py"的结构化指令 → 运行时解析指令 → 真正读文件 → 把内容作为 tool result 塞回上下文 → 再次调用大模型。
- ❌ **三个缺口**：
  1. 工具是怎么定义给模型的？→ **function calling / 工具定义**：Agent 启动时把工具的 JSON Schema（名字、参数、描述）+ system prompt 一起发给模型，模型才知道有哪些工具、参数怎么填。
  2. 循环什么时候停？→ **终止条件**：某轮模型不再发起工具调用（输出纯文本或 stop 信号）→ 运行时检测到"无新工具调用" → 结束循环。
  3. 上下文怎么管？→ 长任务会爆上下文，见 A2。

**标准答法**：
> 用户输入后，Agent 把 **system prompt + 工具定义（JSON Schema）+ 历史对话** 组装成上下文发给大模型。大模型基于上下文**决定**下一步：要么**调用工具**（输出结构化的工具调用指令 + 参数），要么**直接回复文本**表示完成。Agent 运行时（不是模型本身）解析工具调用、真正执行（读文件、跑命令），把执行结果作为一条 tool result 塞回上下文，**再次调用大模型**。模型拿到结果后继续决策。如此循环，直到某轮模型不再发起工具调用（或命中 stop）→ 任务结束。长任务中需做**上下文管理**（摘要压缩、滑动窗口、记忆外存）避免超限。

**四个关键词**：工具定义、决策-执行分离、结果回灌、终止条件。这整个就是 **ReAct 循环**（Reason-Act）。

### 题目 A2：长任务上下文爆了怎么办？

**我的回答**：
1. 比喻"500ML 水杯装 600ML，多出来的 100ML 被丢掉"。
2. 策略：模型配置最大上下文长度，agent 统计当前输入占用，达到 70% 开始压缩，损失部分信息但让模型重新聚焦、减少跑偏。
3. 20 文件改 bug：两种情况——没超容量直接全塞；超了就分批读，第一批读完总结，再读第二批，最后整体总结 + 总结 bug 可能原因。

**点评**：

**第 1 问 ⚠️ 硬伤**：
- "水杯溢出丢最旧"的比喻是**错的**。LLM 上下文不是优雅溢出：
  - **API 层面直接报错**：给 200K 窗口模型发 250K token，返回 400 `context_length_exceeded`，**整个请求失败，什么都不执行**。
  - **框架截断**：从头截断或从尾丢最旧，且会破坏消息结构（工具参数截没了但结果还在），导致模型行为错乱。
  - **准确说法**：上下文窗口是**硬上限**，超了请求直接失败或被强制截断，**不存在优雅溢出**。因此必须在达到阈值（如 70%）**之前**主动管理——不是超了再处理，而是绝不能让它超。
  - **一句话**：上下文窗口是"刹车片"，不是"溢水杯"。超了是事故，不是自动降级。

**第 2 问 ✅ 抓到要点（阈值触发压缩），但只会一招，需补全工具箱**：

| 策略 | 做法 | 适用场景 |
|------|------|---------|
| **摘要压缩** | 把旧对话/工具结果用小模型压成摘要替换原文 | 长对话保主线 |
| **滑动窗口** | 只保留最近 N 轮 + 摘要，旧的直接丢 | 实时性强、历史价值低 |
| **记忆外存** | 内容存外部存储（向量库/DB/文件），需要时检索回来 | 长任务、跨会话记忆（本质 RAG） |
| **主动检索代替塞入** | 不把 20 文件全塞，让 Agent 按需检索相关片段 | 长任务最优解 |
| **工具结果精简** | 工具返回内容先裁剪/摘要再回灌（如只留 diff 不留整文件） | 工具结果过长 |

**第 3 问 ✅ 思路对（分批+摘要合法），但有更优解**：

分批摘要的问题：
1. **压缩丢信息**：改 bug 需要跨文件因果关联（调用方 A + 被调函数 B），摘要最容易丢这种关联。
2. **不知怎么分批**：bug 相关代码可能散在任意文件，无脑分批可能把相关文件拆到不同批次。

**更优解：检索增强（Agent 实际做法）**——别一次性塞 20 文件：
1. 先给 Agent 一个**索引**（文件列表 + 简要说明，体积小），让它规划"大概看哪几个文件、按什么顺序"。
2. Agent **一个/小批量读相关文件**，每读一个提取关键信息，不需要逐字保留的内容做摘要留上下文、原文丢掉；或把文件内容先存**向量库**，Agent 每步语义检索"拉"回最相关片段。
3. 上下文里始终只有"**当前在看的 + 之前提炼的线索**"，而非 20 文件全文。

这其实就是 **Claude Code 在干的事**——从用户视角切到设计者视角就能反推。
**加分哲学**："与其压缩，不如减少塞入"——讲出来比会背压缩算法分高。

**标准答法**：
> 上下文窗口是**硬上限**，超了请求直接失败或被框架强制截断，不存在优雅溢出，必须在达到阈值前主动管理。策略分两类：
> - **压缩类**：摘要、滑动窗口、工具结果精简——减少已有内容体积；
> - **外存类**：记忆存向量库/DB，按需检索回来——从源头减少塞入量（最优解，本质是 RAG）。
> 对"20 文件改 bug"，最优解不是分批摘要，而是**按需检索**：给 Agent 文件索引让它规划，逐个读相关文件、提炼线索、丢原文，或内容先入向量库让 Agent 语义检索——上下文只留"当前关注点 + 关键线索"。

## 模块 B：RAG 工程

### 题目 B1：RAG 是什么？为什么需要它？最简流程几步？追问：为什么不直接全塞上下文？

**我的回答**：听过 RAG，知道"分词 → 计算 → 存向量数据库"，但检索和打分具体怎么搞不懂。

**点评**：
- ✅ 诚实比硬编强太多。且已摸到正确的边："分词、计算、存向量库"三个关键词方向对，只是没串成链 + 用词有误。
- ⚠️ **用词纠正**：RAG 里说的不是"分词"（分词指把一句话切成 token/词，是另一个概念），而是"**切分文档 chunking**"：把长文档切成几百字一段的小块。

**RAG 全链路（必背）**：

**一、离线：把资料变成可检索的向量库**
```
原始文档（PDF/网页/代码）
   ↓  ① 切分 chunk（长文档切成一小段一小段）
   ↓  ② 每段用 embedding 模型算成向量（如 1536 维数组）
   ↓  ③ 向量 + 原文一起存进向量库
```
- **① chunking**：切分策略是 RAG 工程重点（后续单独出题）。
- **② embedding（向量化）**：关键理解——语义相近的文本向量在空间里也相近（"猫"和"小猫"近，"猫"和"汽车"远）。这是 RAG 能"按意思找"而非"按关键词找"的底层原理。
- **③ 存库**：向量 + 原文一起存。原文也要存因为最终喂给大模型的是**原文**不是向量。

**二、在线：用户提问时检索**
```
用户问题："这个函数报错怎么处理？"
   ↓  ④ 把问题也用同一个 embedding 模型算成向量
   ↓  ⑤ 在库里算问题向量与每个文档向量的"距离/相似度"→ 打分
   ↓  ⑥ 取分数最高的 Top-K 段（如最相关 5 段）
   ↓  ⑦ 把这 5 段原文 + 问题一起发给大模型，让它基于资料回答
```
- **⑤ 打分**：算问题向量与每个文档向量的相似度（常用**余弦相似度 cosine**）。分数越高越相关，这动作叫**相似度检索**。
- **⑥ Top-K**：只取最相关几段，不全部返回。
- **⑦ 拼接生成**：检索到的资料塞进 prompt，让模型"看着资料回答"，这就是"增强生成"。

**回答追问：为什么不直接全塞上下文？**（"需要 RAG 因知识截止/会幻觉"对一半，但即使能塞下也该用 RAG）：
1. **资料量超上下文窗口**：企业知识库动辄几 GB、几十万份文档，塞不进任何模型上下文。**物理限制**，没得选。
2. **成本**：每次全量塞入 → token 暴涨 → 费用爆炸 + 响应变慢。RAG 只塞 Top-K，**省钱省时**。
3. **塞太多反而答得更差**（反直觉但真实）：上下文塞太多无关内容，模型被干扰、注意力分散，答案质量下降（叫 **"lost in the middle"** 问题，中间位置关键信息易被忽略）。**少而精 > 多而全**。

**标准答法**：
> RAG = 检索增强生成，分两阶段：
> **离线**：资料切分成 chunk → 每段 embedding 成向量 → 向量+原文存入向量库。
> **在线**：用户问题也 embedding → 在库里算相似度（打分）→ 取 Top-K 最相关段 → 和问题一起喂给大模型生成答案。
>
> 为什么用 RAG 而非全塞上下文：① 资料量超窗口，物理塞不下；② 省成本、提速；③ 塞太多反而干扰模型、质量下降（lost in the middle）。RAG 用"按需检索"替代"全量塞入"。

## 模块 C：Prompt 与结构化输出

### 题目 C1：Function Calling 是什么？和普通 chat API 调用有什么区别？

**我的回答**：（通过代码实践后的理解——`react_minimal_demo.py`）

Function Calling 不是在用另一个 API，还是同一个 chat 端点，只是请求里多了一个 `tools` 参数（工具定义的 JSON Schema）。模型收到请求后，不再只能返回文字，也能返回 `tool_calls`——一个结构化的"我要调 X 工具，参数是 Y"的指令。

完整流程：

```
第1次调 API：
  你 → 模型：用户问题 + tools 列表（如 calculate 工具的定义）
  模型 → 你：tool_calls: [{name: "calculate", arguments: "{"expression": "3*8+72/9"}"}]

执行工具：
  你：真正跑了 do_calculate，拿到结果 "32.0"

第2次调 API：
  你 → 模型：之前的对话 + 工具执行结果 + tools 列表（还在）
  模型 → 你：基于工具结果给出最终文字回答（content 字段，无 tool_calls）

终止条件：模型不再返回 tool_calls → 任务完成
```

**关键认知（来自代码实践，非背书）**：

1. **工具定义是提前塞进请求的**（`tools` 参数），不是中途加的。每次请求都带。模型在整个对话里随时能选任何工具。
2. **模型自己决定调不调工具**——代码里没有任何 `if 用户说计算 then 调工具` 的逻辑，模型读 tools 列表后自主判断。
3. **`msg.get("tool_calls")` 不是字符串匹配**——模型返回的 JSON 被解析成 Python dict，`msg.get()` 是字典 key check，有就取、没有就 `None`。有 tool_calls 走执行分支，没有就走文字输出分支（终止）。
4. **模型可能"不理"你的工具**——直接文字回答不调工具（觉得不需要/工具描述不清晰/Temperature 高导致随机性），这是真实要处理的问题。
5. **当前代码的漏洞**：没处理工具不存在（KeyError）、参数无效、arguments 不是合法 JSON——这些要在 ReAct 循环里补容错。

**面试能讲的额外点**：
- `TOOL_FUNCTIONS = {"calculate": do_calculate}` 是名字到函数的映射表（dict），作用和 PHP 的路由映射一样——用字符串 key 取出处理函数。
- `f"Bearer {API_KEY}"` 是 f-string，Python 的字符串格式化，相当于 PHP 的双引号嵌变量，但必须显式加 `f` 前缀。
- 这和 Claude Code 的机制一模一样：启动时把几十个工具的 JSON Schema 塞进 `tools` 参数，每次请求都带，模型在对话里随时选工具。
