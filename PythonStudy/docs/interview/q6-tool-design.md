# Q6：为什么 AI Agent 工具不是越详细越好？

> 工具 Schema 是给 LLM 看的点菜单，不是给开发看的 API 文档。

---

## 一句话回答

工具描述越详细、参数暴露越多，模型决策准确率反而断崖下跌。核心原则：**业务粗粒度封装、描述极简、参数最小化**。

---

## 为什么越详细越翻车？

### 1. 工具选择准确率断崖下跌

工具调用本质是 LLM 的高维多分类任务。工具数量越多、语义越相似，模型越容易混淆。

| 工具数量 | 选择正确率 |
|---------|-----------|
| 4-6 个 | 高 |
| 20+ 个 | 明显下降 |
| 100+ 个 | 跌到接近随机（~13%） |

描述冗长会让模型抓不住核心触发条件，只靠模糊语义瞎选。典型翻车：查订单调了退款接口、列表查询调了新增接口。

### 2. 参数填充大量报错

Schema 参数堆砌过多、约束模糊、命名不统一 → 模型极易：
- 漏传必填项
- 传错数据类型
- 枚举值越界
- JSON 格式崩坏

### 3. 上下文窗口爆炸

几十个工具的完整 Schema 塞进 System Prompt，动辄上万 Token：
- 推理成本大幅上涨
- 触发窗口截断，部分工具定义被吞掉
- 出现**中间遗忘（Lost in the Middle）**，模型忽略用户核心诉求

### 4. 安全与权限不可控

底层原始接口全暴露给模型，LLM 幻觉下可能调用高危删除、批量修改、数据导出接口。

---

## 正确的工具设计原则

| 原则 | 说明 | 反例 |
|------|------|------|
| **业务抽象** | 封装成业务动作，不暴露底层 API | `handle_data` 万能命名 |
| **描述极简** | 只写：什么时候该调、什么时候禁止调 | 写成了 API 文档 |
| **参数最小** | 只留必填参数，限定类型/枚举/长度 | 把 git status 所有 flag 全暴露 |
| **命名见义** | 一看名字就知道干什么 | `process_query` 模糊名称 |
| **够用就好** | 4-6 个核心工具 > 20 个细分工具 | 每个底层接口都包一个工具 |

---

## 你项目中的实践

```python
# ✅ 好：业务抽象、描述极简、参数最小
{
    "name": "get_status",
    "description": "获取当前工作区文件状态（git status）",
    "parameters": {"type": "object", "properties": {}, "required": []}
}

# ❌ 坏：过度详细、参数冗余
{
    "name": "git_status",
    "description": "调用 git status 命令获取工作区状态，包括已修改、已暂存、未跟踪的文件列表，"
                   "以及当前分支名称、与远程分支的差异、是否处于合并状态等...",
    "parameters": {
        "include_untracked": {"type": "boolean", ...},
        "include_staged": {"type": "boolean", ...},
        "format": {"type": "string", "enum": ["short", "long", "porcelain"], ...},
        "color": {"type": "boolean", ...},
        # ...10 个参数
    }
}
```

## 规模化后的治理方案

工具池膨胀后的解决方案（面试加分点）：

1. **RAG 检索式动态下发**：把工具定义向量化，根据用户意图只检索 Top 3-10 个相关工具，不全量塞 prompt
2. **工具分类树管理**：大类路由（订单类/支付类/用户类），二级菜单按需加载
3. **定期清理冗余**：做工具相似度聚类，下线功能重叠的
4. **调用后置校验**：参数拦截 + 失败语义反馈闭环
5. **多模型兼容**：不同模型对 Schema 解析偏好不同，需要分模型测试回归

---

## 面试话术

> "工具 Schema 是给 LLM 的决策菜单，不是给开发的 API 文档。核心原则：业务粗粒度封装、参数最小化、描述只写触发条件。工具多了用 RAG 检索动态下发，单次只给模型 3-10 个候选。"
