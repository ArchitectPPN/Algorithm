# Agent Harness 能力对照

> 对标来源：力维智联「Agent 平台开发工程师」JD（2026-10 抓取）
> 对照对象：本项目 `agent/` 自研框架（3,614 行）
> 核查方式：逐文件读源码，非按文件名推断

---

## 结论

这条 JD 列出的九项能力，是 Agent Harness 的**完整能力面**，可以直接当参考坐标系。但两个前提必须说清：

1. **它是平台岗，不是应用岗。** 平台岗要求你能「造 harness」，应用岗要求你会「用框架落业务」。你的项目恰好是平台向的，匹配度意外地高——但求职时你大概率投应用岗，两类面试问法完全不同。
2. **JD 不是学习路径。** JD 用「熟悉 / 理解」描述要求，面试问的是「你遇到过什么问题、怎么解决的」。按 JD 逐项打卡会学成一张清单，讲不出故事。

九项现状：**3 项具备、3 项半成品、3 项空缺。**

---

## 一、两个岗位的分界线

| 维度 | Agent 平台开发（这条 JD） | Agent 应用开发（多数招聘） |
|---|---|---|
| 核心工作 | 实现对话循环、工具系统、上下文管理 | 用 LangChain/Dify/自研框架搭业务 |
| 面试追问 | 「你的 loop 怎么保证收敛」「工具失败怎么办」 | 「这个场景为什么用 RAG 不用微调」 |
| 代码量级 | 万行级框架 | 千行级业务集成 |
| 稀缺度 | 高（真正写过 harness 的人少） | 中 |
| 你的匹配 | **高**（3,614 行自研框架） | 中（业务案例偏少） |

一个反直觉的点：正因为投应用岗的人多，自研过 harness 反而是差异化。面试官听到「我自己实现了权限引擎和上下文压缩」，会立刻把你从「调 API 的」里分出来。

## 三、三个值得单独说明的发现

### 1. Skill 这块你比想象中做得好

`build_skills_hint`（`loader.py:96`）只输出 `- {name}: {description}`，**正文不常驻**。激活后由 `agent_loop.py:151` 把 `skill.content` 拼进 user message：

```python
return f"[激活技能: {skill.name}]\n用户输入: {content_after_cmd}\n\n{skill.content}"
```

这就是完整的渐进披露：描述常驻、正文按需。和 Pi 的思路一致，差异只在**激活方式**：

| | Pi | 你的实现 |
|---|---|---|
| 提示词里给什么 | name / description / **location** | name / description |
| 谁负责取正文 | 模型自己用 `read` 读 location | 框架解析标记后注入 |
| 代价 | 多一次工具调用 | 多一轮模型输出标记 |

Pi 的方案省一轮、少一次注入；你的方案**控制权在框架手里**——可以审计激活、可以拒绝、可以记日志。在「验证与审计」这项 JD 要求上，你的设计其实更占优。这点可以在面试里讲成主动选择，而不是「没做成 Pi 那样」。

唯一的缺口是自动激活的闭环：`extract_activation` 写好了但没被调用，实际只有 `/skill-name` 手动触发能走通。

### 2. MCP 是「能造服务，不能当客户端」

`mcp_servers/jira/server.py` 完整实现了 `initialize` / `tools/list` / `tools/call` 的 JSON-RPC 2.0 流程（L295-326），这是**服务端**。

但 agent 侧没有任何 `ClientSession`、`stdio` 连接或工具注入代码。`agent_main.py:65` 定义了 `MCP_FILE`，grep 全文只有定义、无使用。

这意味着：**别人写的 MCP server 你接不进来**。而 JD 说「熟悉 MCP」，面试实际问的是客户端侧——「怎么发现工具、怎么把 MCP 工具转成你的 tool 格式、连接断了怎么重连」。

这个缺口的性价比最高：工作量最小（1–2 天），JD 权重高，且你已经懂协议细节。

### 3. 上下文压缩有两个真实缺陷

**缺陷一：阈值是百分比，不是预算。**

```python
compress_threshold: float = 0.7       # 超过 70% 触发
keep_recent_rounds: int = 10          # 保留最近 10 轮
```

按**轮数**保留下限，不按 token。10 轮短对话可能 2k token，10 轮读大文件可能 50k token——同一个参数在两种场景下差了 25 倍。

Pi 的做法是 `keepRecentTokens = 20000`，从最新往回累加 token 直到预算用尽，**切点跟着 token 走而不是跟轮数走**。

**缺陷二：压缩失败会静默丢历史。**

```python
except Exception as e:
    print(f"  [⚠️ 上下文] 压缩失败: {e}，保留最近 {len(recent)} 条")
    return recent        # early 全部丢弃，连摘要都没有
```

摘要失败时直接返回 `recent`，早期历史**无损丢失且无提示**。用户看不到、日志里只有一行 print。这是数据丢失级的问题，不是体验问题。

Pi 的对应设计是原始记录永不删除，只往会话里插入一条 summary entry——压缩是「追加」不是「替换」，失败了最多是摘要没生成，历史还在。

## 四、缺口优先级

排序依据不是 JD 顺序，而是 **投入产出 × 面试频率**。

| 优先级 | 缺口 | 工作量 | JD 权重 | 简历价值 | 说明 |
|---|---|---|---|---|---|
| **P0** | MCP client | 1–2 天 | 高 | 中 | 协议已懂，只缺连接与注入；面试必问 |
| **P0** | 可观测性 | 2–3 天 | 中 | **高** | 唯一「一份投入两份产出」的项，见下 |
| **P1** | 审计日志 | 0.5 天 | 高 | 中 | 权限引擎已有钩子，加 append-only JSONL 即可 |
| **P1** | 压缩修正 | 1 天 | 中 | 低 | 修缺陷二（静默丢历史）是正确性问题，优先于改造 |
| **P2** | 沙箱 | 3–5 天 | 高 | 中 | 平台岗核心，应用岗可只讲原理 |
| **P3** | 并行执行 / terminate 三态 | 1–2 天 | 低 | 低 | 属于把 Pi 的设计搬过来，非必需 |

### 为什么可观测性排在 P0

它是唯一同时解决两个问题的项：

1. 直接满足 JD 第 8 项（性能与可观测性）
2. **产出简历需要的量化数字**——token 消耗、平均轮次、工具成功率、P95 延迟、压缩前后 token 降幅

第 2 点很关键。你之前担心「RAG 软暂停导致 Week8 评估专题搁置、简历缺量化数据」。现在有更好的解法：**不必回 RAG 做评估，直接在 agent 上做可观测性**。产出的数字对 agent 岗比 `Recall@K` 更对口：

| 原计划产出 | 现在的替代产出 | 哪个更对口 agent 岗 |
|---|---|---|
| Recall@5 从 0.6 → 0.85 | 上下文压缩使单轮 token 降 62% | 后者 |
| LLM-as-Judge 评分 | 7 工具端到端成功率 94% | 后者 |
| 检索延迟 | 平均 3.2 轮收敛，P95 延迟 8.4s | 后者 |

而且这些数字从可观测性里**自动产生**，不需要额外做一次评估实验。

## 五、与 transition-plan 的映射

这份 JD 的九项，跟原计划**第 10–14 周（工程化）**高度重合，只是换了平台岗的语言：

| JD 能力 | 原计划对应周次 | 备注 |
|---|---|---|
| 沙箱与隔离 | 第 10–11 周（Celery/Redis、持久化） | 原计划讲异步与持久化，隔离是同一层 |
| 性能与可观测性 | 第 9 周（LangFuse） | RAG 软暂停时被搁置，现在可提前 |
| 验证与审计 | 第 12 周（Docker/CI/CD） | CI 里的权限与审计 |
| MCP | 未在原计划中 | **计划外新增，但 JD 权重高** |

这说明转型计划的方向是对的，只是**优先级需要调**：原计划按「异步 → 持久化 → 容器 → CI」推进，而按 JD 权重，MCP 与可观测性应该提前。

一个可行的调整：RAG 软暂停后的空档（原本给 Pi 学习的 6 天），改为「MCP client + 可观测性」两个 P0 项。Pi 学习的 A 类项目顺延，因为它们本来就是改造 `agent/` 时顺手做的事。

## 六、每项在面试里怎么讲

面试官不会问「你熟不熟悉沙箱」，会问「工具执行危险命令你怎么防」。对照表：

| 能力 | 会被问什么 | 你的答法要点 |
|---|---|---|
| 对话循环 | 怎么保证一定会停 | 不要答 `max_rounds`。答「模型不再产生 tool call 即收敛，硬上限只是保险」，然后讲终止信号的聚合语义 |
| 工具系统 | 工具执行到一半失败怎么办 | 讲三态：成功 / 业务失败（`isError`）/ 抛异常，三者对模型语义不同 |
| 上下文与记忆 | 上下文满了怎么办 | 讲阈值公式而非百分比；讲「压缩是追加摘要，不是删除历史」 |
| Skill | 技能多了会不会撑爆提示词 | 讲渐进披露：描述常驻、正文按需，给 token 数字 |
| MCP | 怎么接第三方工具 | 讲握手（initialize）、工具发现（tools/list）、schema 转换、断线重连 |
| 沙箱 | 模型执行 `rm -rf /` 怎么办 | 讲三层：静态规则拦截 → 危险命令识别 → 进程隔离与资源限额 |
| 验证与审计 | 怎么追溯一次误操作 | 讲 append-only 日志：谁、何时、哪个工具、什么参数、结果、谁批准的 |
| 可观测性 | 怎么知道 agent 变差了 | 讲四个指标：token/轮、工具成功率、P95 延迟、人工干预率 |
| 异常处理 | 模型 API 挂了怎么办 | 讲重试策略、降级、错误结构化进消息而非抛出 |

**共同规律**：每一项都要有「我遇到过什么」的具体故事。只有清单没有故事，面试官会判定为「看过文档」。
