## 验收：8 道思想题（答完贴回核对）

> 只问"为什么这样设计"，不问字段名和类型写法。答得出来才说明思路拿到了；
> 有任何一道讲不清，Day01 不算通过。

1. Agent 运行中用户插话，为什么既要"立刻生效"，又要"等闲下来再处理"两种？只留一种会坏在哪？
   - 参考：steering 语义是“纠正方向”，要尽快进入上下文；follow-up 语义是“接续任务”，要等本轮自然结束。只有 steering 会让所有消息都打断当前任务、丢失“干净收尾”的时刻；只有 follow-up 会让纠偏太晚，用户只能整体中止并重发，且模型可能重复同样错误。真正“立刻中断已执行命令”依赖 AbortSignal，与消息队列是三条不同通道。
2. 危险命令（如 `rm -rf`）该在哪一层拦？为什么不能靠"用户发消息叫停"来兜底？
   - 参考：必须在执行前的 `beforeToolCall` 拦截，逐工具同步检查；等用户发消息叫停时命令已执行，损失已发生，消息通道救不了已开始的操作。真正“中止正在执行”依赖 AbortSignal，与消息队列不同。
3. 为什么 Pi 允许工具自己声明"干完了就停"，而不是让框架统一判断？
   - 参考：不是框架不能统一判断，而是框架判断不了。框架只看到 ToolResult，不知道这个工具的业务语义；同一返回 20 条记录，查询类工具该停，中间步骤工具必须继续。终止点取决于业务状态，只有工具作者在 execute() 返回时才知道，所以 Pi 把 terminate 作为返回值下放。
4. 一批里 3 个工具，只有 1 个说"停"，Pi 要求全员同意才停。这个"悲观聚合"在保护什么？换成"任一同意就停"会出什么事故？
   - 参考：批是 N 对 N 协议的语义单元，模型一次发起 3 个调用就必须拿到 3 个结果才能继续。任一 true 就停会破坏协议，导致模型对任务状态认知错误，可能在残缺上下文下继续决策。必须全员同意才停，保护批内完整性。
5. 模型报错或用户中止时，为什么钩子不该有权说"继续"？这条规则背后的原则是什么？
   - 参考：原则是“安全阀优先于扩展点”。① 钩子不能替用户做决定，用户已明确停止就不能再跑；② 模型报错（如 429 额度限制）继续调用只会继续失败，重试应由上层策略决定而非钩子硬拽；③ 循环对 error/aborted 的退出判定是硬出口，扩展点只能在正常路径上做决定，无权覆盖。
6. 为什么"换模型"要放在每轮请求前，而不是放在一轮结束后？
   - 参考：模型选择是“请求的参数”，不是“轮次的产物”。换模型必须在真正发请求时确定，才能覆盖首次请求、重试请求及压缩上下文后的请求；一轮结束只是这些请求时机的一部分。若在轮末暂存-下一轮取用，等于自造一层状态且会漏掉首次请求。Pi 用 prepareRequest 管常驻设置（每次请求都生效），prepareNextTurn 管一次性补丁（只影响下一轮），职责分明。
7. 为什么"改上下文"和"插消息"要分成两个钩子，合成一个会有什么问题？
   - 参考：改上下文（系统提示/工具/配置）在任何请求前都安全；插消息要求消息队列为空，否则插进去的消息会排在所有排队消息（steering/follow-up）之后，顺序混乱。prepareRequest 在每次请求前调用但消息已追加完毕，故返回类型 Omit 掉 messages 字段类型级禁止；prepareNextTurn 在一轮结束时调用，此时队列为空，插入消息会放在最前面，语义正确。两件事时序约束不同，合成一个钩子无法同时满足。
8. Pi 把 Agent 循环拆成外层和内层两层，各管什么？只留一层会缺什么能力？
   - 参考：内层管“单任务执行”，即模型请求、工具调用、steering，终止条件是本轮无事可做；外层管“会话接续”，内层退出时检查 follow-up 并把它塞回内层，实现会话续航。两层对应不同生命周期：内层是任务生命周期，外层是会话生命周期。若只留一层，就无法区分任务结束与会话结束，也无法处理显性 continue 决策——内层的自然继续条件用尽后，外层提供兜底再补一轮。

## Agent 循环时序图（学习者整理 2026-11-05）

```text
while (外层循环: 会话续航)
    取出 followUp 消息        # 上一轮跑完后才检查, 有则进入内层

    while (内层循环: 单任务)   # 条件 = 有工具结果要回喂 OR 有消息待处理
        prepareNextTurn        # 非首轮才调: 一次性补丁(可换模型/上下文/插消息)
        取出 steering 消息      # 用户运行中插话, 追加进对话
        declareToolChanges     # 工具集增删 → 同步成 system 消息
        prepareRequest         # 每次请求前: 常驻设置(换模型/上下文, 禁插消息)

        调用模型 (stream)
            error / aborted    # 硬出口 → finishTurn → agent_end, 钩子无权拦

        for 每个工具调用 (批内, sequential 或 parallel)
            beforeToolCall     # 可 block 单个调用; block+terminate 可写终止标记
            execute()          # 执行工具, 可自设 terminate (业务状态决定)
            afterToolCall      # 可改结果, 可覆盖 terminate

        批末聚合               # every(terminate===true) → 全员同意才停
        finishTurn             # end=立即退出 / continue=保活 / 无=按默认走
        再取 steering           # 有则继续内层下一轮

    检查 followUp              # 检查是否需要退出循环: 无 followUp → agent_end 退出; 有 → 塞回内层再跑
```

三个关键修正（对照初学者常见误区）：

- **工具调用 for 循环在模型调用之后**，不是循环开头——顺序是：准备上下文 → 调模型 → 模型吐出 tool_calls → 逐个执行
- **steering 有两次取点**：调模型前处理积压的（图上部），工具批跑完后再取一次（图下部），后者决定内层是否继续
- **prepareRequest 在调模型前**，不是和工具调用平级——它决定的是"这次请求用什么模型/上下文"
